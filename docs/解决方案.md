# Semantica Graph Engine — 解决方案（MVP）

> 状态：设计方案 v1（2026-08-19）
> 范围：把已安装的 `semantica 0.6.5` 封装为独立对外服务的图引擎，供 `/home/open-ikc` 的图谱服务能力消费；
> 对外提供 **HTTP / gRPC / Celery / MCP / CLI** 五类接口。本文先给方案，MVP 按里程碑落地。

## 1. 现状盘点

### 1.1 当前目录（semantica-graph-server）
- 仅含 `.venv`，其中安装 `semantica 0.6.5`（github.com/semantica-agi/semantica）。
- 可用组件（已实测导入）：
  - `semantica.kg`：`GraphBuilder.build()`、`EntityResolver`、`GraphAnalyzer`、`PathFinder`、`CentralityCalculator`、`CommunityDetector`、`NodeEmbedder`、`ProvenanceTracker`、时态图谱。
  - `semantica.export`：`JSONExporter / CSVExporter / RDFExporter / ArrowExporter / ParquetExporter / GraphExporter` 等。
  - `semantica.triplet_store.OxigraphStore`：基于 `pyoxigraph` 的嵌入式 RDF 存储（已装 `pyoxigraph 0.5.9`）。
  - `semantica.graph_store`：Neo4j / FalkorDB / AGE / Neptune 等**外部图库后端**（MVP 不启用，保留扩展位）。
- **环境问题**：`semantica.context` / `semantica.vector_store` 导入链因 pinecone 包改名冲突（装了 `pinecone-client` 旧包，`import pinecone` 期望新包）而报错。影响：semantica 自带的 `mcp_server`（依赖 ContextGraph）不可用。
  - 对策（MVP）：引擎**不 import 该损坏链路**，自建 MCP 服务；后续 `pip install "pinecone>=5"` 或卸载冲突包后可切换 semantica 原生能力。

### 1.2 open-ikc 图谱服务现状（占位实现）
- 形态：`kbMode=graph` 知识库 + `graphSchema`（`entityTypes[] / relationTypes[]`，relation 可带 `sourceTypes/targetTypes`）。
- 数据：进程内 dict（`app/services/graph_store.py`，`GraphStore` 类变量），无持久化。
- 接口：`GET /api/v1/knowledge-bases/{kb_id}/graph/stat|nodes|edges|neighbors|export`，响应 envelope `{traceId, errCode, errMsg, data}`。
- 建图：`GraphService.build_from_doc()` 由解析成功链路联动调用，当前**占位**（每文档一个实体节点）。
- 稳定 ID：`graph_{sha1(kbId)[:12]}`、`ent_{sha1(graphId:type:normalizedName)[:12]}`、`rel_{sha1(graphId:type:source:target)[:12]}`。
- SDK：`open_ikc_sdk`（models/graph.py、MCP 封装 REST、typer CLI）；协议以 `AGENTS.md` + 代码为准。

### 1.3 结论
open-ikc 需要的是一个**独立的、可持久化的、可被异步/同步调用的图引擎**；当前占位实现的所有查询语义（稳定 ID、增量合并、证据、置信度、schema 覆盖率、增量废弃）应完整迁移到引擎侧并保持一致，open-ikc 退化为薄客户端。

## 2. 引擎总体设计

### 2.1 分层架构

```
┌────────────────────────────────────────────────────────────┐
│  interfaces（协议面）                                        │
│  HTTP(FastAPI) · gRPC(dynamic descriptor) · Celery ·       │
│  MCP(stdio JSON-RPC) · CLI(typer)                          │
├────────────────────────────────────────────────────────────┤
│  application：GraphEngineService（用例编排，五面共用同一逻辑） │
├────────────────────────────────────────────────────────────┤
│  domain：图模型/稳定ID/graphSchema校验/合并规则/错误码         │
├────────────────────────────────────────────────────────────┤
│  adapters：                                                │
│   semantica（GraphBuilder/EntityResolver/Analyzer/export）  │
│   persistence（SQLite 主存储 + 可选 Oxigraph RDF 视图）       │
└────────────────────────────────────────────────────────────┘
```

设计要点：
- **一个应用层、五个协议面**：HTTP/gRPC/Celery/MCP/CLI 只做协议适配，不复制业务逻辑；保证语义一致、可联调。
- **契约优先**：统一 DTO（entity/relation 记录）与响应 envelope 沿用 open-ikc 现有格式（`{traceId, errCode, errMsg, data}`，错误码 2xxxxx 风格），open-ikc 可零成本替换。
- **多租户**：graph 资源携带 `tenantId / ownerId`（透传 open-ikc AUTHZ 头），所有查询按 namespace 隔离。
- **持久化**：MVP 用 SQLite（WAL，三表 `graphs / entities / relations`），保证重启不丢；图构建/分析/导出能力由 semantica 提供；RDF/SPARQL 能力后续通过 `OxigraphStore` 视图补强（预留接口位）。

### 2.2 能力映射：open-ikc 定义 ↔ semantica 能力

| open-ikc 概念 | 引擎实现 | semantica 组件 |
| --- | --- | --- |
| graphSchema 校验 | domain.schema.validate | 自定义（规则一致） |
| 稳定 ID（graph/ent/rel） | domain.ids（沿用原 sha1 规则） | — |
| 建图（抽取结果→图） | application.build / merge | `kg.GraphBuilder.build()`（合并、去重） |
| 实体对齐/别名累积 | domain.merge（aliases 并集、evidence 去重、confidence 取大） | `kg.EntityResolver`（可选增强） |
| 统计/类型分布 | application.stat | `kg.GraphAnalyzer`（度数/连通分量等扩展指标） |
| 邻域/路径 | application.neighbors / paths | `kg.PathFinder`（扩展） |
| 导出 jsonl | application.export | `export.JSONExporter` / `CSVExporter`（RDF 走 pyoxigraph） |
| 证据/置信度/状态 | entity/relation 记录字段 | `kg.kg_provenance`（ProvenanceTracker 扩展） |

### 2.3 对 open-ikc 图谱服务定义的修正建议（引擎落地时同步优化）

1. **图谱升级为一级资源**：`graphId` 独立于 `kbId` 存在（保留 `graph_{sha1(kbId)[:12]}` 规则），新增 `POST /graphs`、`GET /graphs/{id}`、`DELETE /graphs/{id}`；open-ikc 侧维持 `kbId ↔ graphId` 映射，行为不变。
2. **补齐写接口**：open-ikc 目前只有只读视图 + `build_from_doc`；引擎新增 `build`（文本/抽取记录）、`merge`（增量 upsert）、`deprecate-doc`（按 docId 增量废弃），open-ikc 的 `build_from_doc` 直接映射到 `merge + deprecate-doc`。
3. **校验下沉**：graphSchema 校验、类型约束、置信度区间、evidence 结构校验全部由引擎执行并返回统一错误码；open-ikc 不再重复实现。
4. **统一证据结构**：`evidence[] = {docId, pageId?, chunkId?, quote?}`，替代现占位结构的松散 dict。
5. **扩展查询语义**：`paths`（最短路径）、`analytics`（度数/连通分量）、`nodes/edges` 增加 `name/属性过滤`，均作为引擎能力，open-ikc 按需透出。
6. **异步化**：`build` 支持 `async` 模式（登记 job 返回 jobId，Celery 启用时投递执行）；`merge/export` 暂无 async 参数。open-ikc 解析链路可选异步联动，避免同步阻塞。

## 3. 对外接口定义（MVP）

### 3.1 统一协议
- 响应：`{"traceId": "...", "errCode": "0", "errMsg": "", "data": {...}}`
- 错误码：`0` 成功；`200001` 参数非法；`200404` 不存在；`200409` 冲突；`200500` 内部错误。
- DTO：
  - entity：`{entityId, type, name, properties, aliases, evidence, confidence, status, createdAt, updatedAt}`
  - relation：`{relationId, type, sourceEntityId, targetEntityId, properties, evidence, confidence, status, createdAt, updatedAt}`

### 3.2 HTTP（FastAPI，默认端口 18010，前缀 `/api/v1/graph`）
| Method | Path | 说明 |
| --- | --- | --- |
| POST | `/graphs` | 创建图（含 graphSchema 校验） |
| GET | `/graphs/{graph_id}` | 图元信息 + stat |
| DELETE | `/graphs/{graph_id}` | 删除图 |
| GET | `/graphs` | 图列表（按 tenant/owner 过滤） |
| POST | `/graphs/{graph_id}/build` | 建图（records 或 text；async 可选） |
| POST | `/graphs/{graph_id}/merge` | 增量合并实体/关系 |
| POST | `/graphs/{graph_id}/deprecate-doc` | 按 docId 增量废弃 |
| GET | `/graphs/{graph_id}/stat` | 统计 + schema 覆盖率 |
| GET | `/graphs/{graph_id}/nodes` | 分页节点（entityType/name 过滤） |
| GET | `/graphs/{graph_id}/edges` | 分页边（relationType 过滤） |
| GET | `/graphs/{graph_id}/neighbors` | 邻域（depth 1/2） |
| GET | `/graphs/{graph_id}/paths` | 最短路径（扩展） |
| GET | `/graphs/{graph_id}/analytics` | 图结构分析（semantica GraphAnalyzer 扩展指标） |
| GET | `/graphs/{graph_id}/export` | 导出（jsonl/json） |
| POST | `/jobs/{job_id}/run` | 同步执行已登记 job |
| GET | `/jobs/{job_id}` | job 状态/结果查询（async 轮询用） |
| GET | `/jobs` | job 列表（graphId/limit 过滤） |
| GET | `/health` `/ready` | 存活/就绪 |

### 3.3 gRPC（`proto/graph/v1/graph.proto`，默认端口 50051）
- `GraphService`：`CreateGraph / GetGraph / DeleteGraph / ListGraphs / BuildGraph / MergeRecords / DeprecateDoc / Stat / ListNodes / ListEdges / Neighbors / Paths / ExportGraph / RunJob / GetJob`（后两者对应 HTTP job 端点）
- 全部消息复用统一 envelope（`trace_id/err_code/err_msg/data`），与 HTTP 语义一一对应。
- 环境无 `grpc-tools`：MVP 采用**运行时动态 descriptor**（`FileDescriptorProto` + `message_factory` + `grpc` generic handler）实现服务端与客户端，避免离线生成；proto 文件保留为权威契约，接入 CI 后可切 grpc_tools 生成。

### 3.4 Celery（broker/backend 默认 `redis://localhost:6379/0`，`GRAPH_ENGINE_CELERY_BROKER/BACKEND/ENABLED` 可 env 覆盖）
- 注册任务（与 HTTP async、job 机制共用同一 application 层）：`graph_engine.build`（覆盖 build / build_text 两类 job；text 建图时把 text/title 一并投递）、`graph_engine.merge`、`graph_engine.deprecate_doc`、`graph_engine.export`。
- async 投递语义：HTTP `build` 带 `async=true` 时先 `submit_job` 登记 pending job（响应 jobId），Celery 启用（`celery_enabled`）时再经 `dispatch_job` 投递 broker，worker 成功后回写 job 状态（含 result），调用方以 `GET /jobs/{job_id}` 轮询；未启用时仅登记 pending、不触碰 broker，可经 `POST /jobs/{job_id}/run` 手动同步执行（成功/失败均回写状态）。`merge/export` 暂无 async 参数（HTTP 同步直连）。注：worker 执行**异常**时任务抛错、job 暂保持 pending（失败自动回写/重试列为后续增强）。
- Docker compose 栈不启动 redis 容器，Celery broker/backend **默认指向宿主本地 redis**（经 `host.docker.internal:6379`，密码默认 `1qaz2wsx3edc`，可在 `.env` 用 `CELERY_BROKER_URL` 覆写）并默认启用 Celery；本地开发默认关闭（仅登记、不投递），`graph-engine serve worker` 消费任务。宿主 redis 需监听 `0.0.0.0` 且开启密码，engine 容器才能访问。

### 3.5 MCP（stdio，`graph-engine serve mcp`）
- 自建轻量 JSON-RPC over stdio（与 semantica 自带 mcp_server 同思路，但**不依赖损坏的 context 链路**）。
- 工具（17 个）：`graph_create / graph_list / graph_get / graph_delete / graph_stat / graph_nodes / graph_edges / graph_neighbors / graph_paths / graph_build / graph_merge / graph_deprecate_doc / graph_export / graph_job_run / graph_job_get / graph_search / graph_index_status`。
- 其中 `graph_search / graph_index_status` 为语义检索骨架（守卫式探测 semantica `vector_store/context/embeddings` 检索链，不可用或未配置检索后端时确定降级：`semantica:false`、`hits:[]`），真实语义链待 venv 依赖（pinecone 冲突）修复后激活。

### 3.6 CLI（typer，`graph-engine`，退出码约定同 open-ikc `ikc`）
- `graph-engine serve http|grpc|mcp|worker`
- `graph-engine create|list|get|delete|stat|build|merge|deprecate-doc|nodes|edges|neighbors|paths|export|analytics ...`（graph 资源命令均为顶层子命令）
- `graph-engine job-run|job-get|job-list <jobId> ...`（任务同步执行/状态查询/列表）


## 5. MVP 里程碑与验收

| 里程碑 | 内容 | 验收 |
| --- | --- | --- |
| M0 | 环境确认：semantica 可用面、依赖清单、pinecone 隔离 | `pytest` 冒烟通过 |
| M1 | domain + SQLite + application（build/merge/stat/nodes/edges/neighbors/export/deprecate） | 单测：ID 稳定、合并规则、增量废弃 |
| M2 | HTTP + CLI + tests | `curl` 全端点 + `graph-engine graph ...` 走通 |
| M3 | gRPC 服务 + 客户端 | 与 HTTP 同用例对拍 |
| M4 | Celery 任务 + job 查询 | worker 处理 build/export 任务 |
| M5 | MCP stdio 服务 | JSON-RPC `initialize/list_tools/call_tool` 走通 |
| M6 | open-ikc 集成：`graph_store.py` 替换为引擎 client | open-ikc 图谱接口行为不回归 |

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| `semantica.context/vector_store` pinecone 冲突 | MVP 不导入该链路；记录修复步骤（`pip install "pinecone>=5"`） |
| torch / sentence-transformers 重依赖、无网环境 | MVP 不做 LLM/embedding 抽取；build 接受显式 records，text 走规则抽取 |
| `grpc-tools` 缺失 | 动态 descriptor 实现 gRPC；proto 为权威契约 |
| `mcp` 包缺失 | 自研 stdio JSON-RPC（对齐 MCP 规范最小子集） |
| open-ikc 为占位实现 | 以 `AGENTS.md` + 代码为准，engine 保留其 DTO/envelope/ID 规则兼容 |

## 7. 后续演进（MVP 之后）
- 切换 semantica `graph_store` 外部后端（Neo4j/FalkorDB）作为大图存储。
- 接 `OxigraphStore` 提供 SPARQL / RDF 视图；接 LLM 抽取（`semantic_extract.LLMExtractor`）增强建图。
- 全量 open-ikc 侧改造：`build_from_doc` 异步化、graphSchema 校验下沉、catalog/文档同步。
