# Semantica Graph Engine 功能清单

> 把已安装的 `semantica`（0.6.5）封装为独立对外服务的图引擎，供 open-ikc 消费；对外提供 HTTP / gRPC / Celery / MCP / CLI 五类接口。

| 一级功能 | 二级功能 | 功能描述 |
| --- | --- | --- |
| 一、图谱实例管理 | 创建图谱实例 | 按 `kbId` 创建图谱，校验并归一化 `graphSchema`，自动派生稳定 `graphId`（`graph_ + sha1(kbId)[:12]`），支持 `tenantId`/`ownerId` 归属划分与 `graphId` 显式指定 |
| 一、图谱实例管理 | 查询实例元信息 | 按 `graphId` 获取单个图谱元数据（名称、kbId、schema 快照、节点/边计数、时间戳） |
| 一、图谱实例管理 | 列出图谱实例 | 列举全部图谱，支持按 `tenantId`、`ownerId` 过滤 |
| 一、图谱实例管理 | 删除图谱实例 | 删除图谱并级联清理实体/关系记录、作业、约束画像与本体快照 |
| 一、图谱实例管理 | 稳定 ID 生成 | 与 open-ikc 完全兼容的 ID 派生规则：`graphId = graph_ + sha1(kbId)[:12]`、`entityId = ent_ + sha1(graphId:type:normalizedName)[:12]`、`relationId = rel_ + sha1(graphId:type:source:target)[:12]`，实体名先归一化（去空白标点、统一小写），保证跨系统 ID 一致 |
| 一、图谱实例管理 | graphSchema 校验 | 与 open-ikc `validate_graph_schema` 同口径：`entityTypes`/`relationTypes` 必须为数组、类型非空且不重复、`sourceTypes`/`targetTypes` 必须为字符串数组（均附 `field`/`reason`）；建图时实体/关系类型未在 schema 声明则按 `200001` 拒绝（schema 声明了类型才校） |
| 二、文档加工与知识抽取 | 按记录建图（build） | 核心加工入口：schema 校验 → 稳定 ID 派生 → semantica `GraphBuilder` 建图 → 增量 upsert 入库；响应回传**已决策记录**（`entities`/`relations`），供 core 直接落库、不重做抽取 |
| 二、文档加工与知识抽取 | 按文本建图（build text） | 文档标题 + markdown 结构术语（标题/粗体/行内代码）与「引号词」（`「…」`/`“…”`）派生候选实体（长度 2~40、按归一化名去重、上限截断保证确定性）；同句共现抽关系（切句 → 正文可定位 → 无序对去重 → 按 `graphSchema` 定类型 → 置信度两端取小），不依赖 LLM、不联网 |
| 二、文档加工与知识抽取 | 增量合并（merge） | 对已有实体/关系按稳定 ID 增量 upsert：别名并集、证据去重追加、置信度取大、保留首次 `createdAt`；既有记录优先复用，重复构建只收敛不膨胀 |
| 二、文档加工与知识抽取 | 按文档废弃（deprecate-doc） | 按 `docId` 增量废弃该文档产出的实体与关系，标记 `deprecated` 而非物理删除 |
| 二、文档加工与知识抽取 | 多来源溯源与证据 | 每条实体/关系维护 `evidence`（docId + 原文片段 + 抽取方法）与 `docId`/`properties`，支持跨文档同名对齐与来源追溯 |
| 二、文档加工与知识抽取 | 本体感知校验（schemaCheck） | 构建后按 `graphSchema` 做实例级一致性检查（端点类型 / 必填 / 基数 / 数据类型），越界**只计数告警不阻断**（D4/D5 口径） |
| 三、抽取约束画像（人工修正沉淀） | 约束画像四件套 | `entityTypes`（锁定实体类型）/ `entityRenames`（别名改名，原名进 `aliases` 保召回）/ `entityBlacklist`（软删不入库）/ `examples`（few-shot 样例，展开并入前三张表并落 `relationTypes`） |
| 三、抽取约束画像（人工修正沉淀） | 按图持久化沉淀 | 画像持久化至 `graph_constraints`（SQLite 表 / Neo4j `:GraphEngineGraphConstraint`），后续任何直接打到引擎的构建（含 worker 复用旧载荷）同样生效；非法条目守卫式忽略，不拖垮构建 |
| 三、抽取约束画像（人工修正沉淀） | 在稳定 ID 前生效 | 文本建图在**派生稳定 ID 之前**应用约束（改名会改 ID，是期望语义）；记录建图只做黑名单 + 关系端点级联（改名会打断端点，故不允许在记录路径改名） |
| 三、抽取约束画像（人工修正沉淀） | 关系端点定类型 | 人工确认的端点对 → 关系类型，键支持 `A\|B` / `A->B` / `A,B` / `[A,B]` 四种形态，按**无序对**匹配（A→B 与 B→A 同键） |
| 三、抽取约束画像（人工修正沉淀） | 画像读写与收敛统计 | `GET /graphs/{id}/constraints`（缺画像返回空画像、不报错）与 `PUT`（整体替换，返回摘要）；build 响应附 `constraints`（applied 统计 + renames/types/blacklist/relationTypes/examples 条目数） |
| 四、查询与检索 | 统计信息（stat） | 返回节点/边计数、活跃/废弃口径、实体与关系类型分布（`TypeCount`）及 `schemaCoverage`（按 graphSchema 的类型覆盖率） |
| 四、查询与检索 | 节点查询（nodes） | 分页查询实体节点，支持 `entityType`、`name` 过滤，输出含 `totalPages` 契约字段 |
| 四、查询与检索 | 边查询（edges） | 分页查询关系边，支持 `relationType` 过滤 |
| 四、查询与检索 | 邻域查询（neighbors） | 按 `entityId` 返回实体邻域子图，支持 `depth` 1/2 |
| 四、查询与检索 | 路径查询（paths） | 两点间最短路径（`GraphPath`），支持 `maxDepth`（默认 5） |
| 四、查询与检索 | 图分析（analytics） | 调用 semantica `GraphAnalyzer` 输出分析结果（中心性/度分布），semantica 不可用时确定降级 |
| 四、查询与检索 | 语义检索（search） | 缺省内置词法后端 `builtin-lexical`：在图内活跃记录上现算确定性打分召回（无外部索引、写入立即可检索）；向量后端可按 `RetrievalBackend` 契约注入替换；检索链不可用时降级返回 `semantica:false` + 空 `hits` |
| 四、查询与检索 | 检索能力探活（index-status） | 回报检索/向量链可用状态与实际生效后端名，供运维判断「命中是谁给的」 |
| 四、查询与检索 | SPARQL 查询（sparql） | 以 pyoxigraph 构建当前图的只读 RDF 视图（稳定 ID → 稳定 IRI，谓词命名空间 `urn:ge:kg#`）；白名单只允许 `SELECT/ASK/CONSTRUCT/DESCRIBE`；`GRAPH_ENGINE_SPARQL_TIMEOUT`（默认 10s）+ `SPARQL_MAX_ROWS`（默认 5000）双护栏；`pyoxigraph` 不可用时确定降级 |
| 四、查询与检索 | 导出（export） | jsonl / json 原生导出，以及 RDF 系格式 `turtle/ttl/nt/nq/rdfxml`（经 RDF 视图，缺依赖时降级） |
| 五、异步任务与作业调度 | 异步作业登记（submit_job） | 请求带 `async=1` 时先校验图谱存在，再登记为 job 返回 `jobId`（状态 `pending`），文本/记录建图分派为 `build_text` / `build` 两类任务 |
| 五、异步任务与作业调度 | Celery broker 投递 | 登记后投递 Redis broker，支持单机与哨兵（`GRAPH_ENGINE_CELERY_SENTINEL_NODES`）模式；未启用或 broker 不可达时仅保持 `pending`，不静默丢失 |
| 五、异步任务与作业调度 | 作业手动执行（run_job） | 同步执行已登记任务，供 HTTP `jobs/{id}/run` 与 Celery worker 复用；终态统一回写（成功 `success`+result / 失败 `failed`+error，失败也上抛，避免作业卡在 `pending`） |
| 五、异步任务与作业调度 | 作业状态查询（get_job） | 按 `jobId` 轮询作业状态与结果，本地态 `status` + 映射后的外部态 `taskStatus`（未知态 fail-closed = `FAILED`） |
| 五、异步任务与作业调度 | 作业列表（list_jobs） | 按图谱列举作业，支持 limit（默认 20） |
| 五、异步任务与作业调度 | 六类异步任务 | Celery 任务：`graph_engine.build / merge / deprecate_doc / export / ontology_candidates / ontology_validate_graph` |
| 六、多协议接口层 | HTTP 接口 | FastAPI，前缀 `/api/v1/graph/*`（33 条路由），响应 envelope 与 open-ikc 对齐，错误码统一映射 HTTP 状态（200001→400 / 200404→404 / 200409→409 / 260009→501 / 其他→500） |
| 六、多协议接口层 | gRPC 接口 | `graph.v1.GraphService`（24 个 RPC，Envelope 线缆），运行时动态 descriptor 实现（离线无 grpc-tools 亦可），`proto/graph/v1/graph.proto` 为权威契约，默认端口 50051 |
| 六、多协议接口层 | Celery Worker 接口 | `graph-engine serve worker`，消费 Redis 队列执行异步作业，进程内重建日志投递 |
| 六、多协议接口层 | MCP 接口 | stdio JSON-RPC 实现 `initialize / tools/list / tools/call`，28 个工具与 HTTP/gRPC 语义一一对应（`analytics` 仅 HTTP/CLI 提供） |
| 六、多协议接口层 | CLI 接口 | typer 命令行 `graph-engine`，子命令扁平（`create/list/get/delete/stat/build/merge/deprecate-doc/nodes/edges/neighbors/paths/export/sparql/analytics/ontology-*/job_*` + `serve`），退出码 0/1/6 约定对齐 open-ikc |
| 六、多协议接口层 | 健康与就绪探针 | `GET /health`、`GET /ready`（探针请求不进访问日志与日志中心，避免淹没业务日志） |
| 六、多协议接口层 | 链路追踪 | HTTP 中间件按契约头优先级提取并用 `normalize_trace_id` 归一（非法值重新生成，禁止继续透传），绑定 contextvar 贯穿请求-响应与每条日志 |
| 六、多协议接口层 | 错误码与稳定码 | 2xxxxx 风格（`200001` 参数 / `200404` 不存在 / `200409` 冲突 / `200500` 内部）+ 本体域 `260xxx`（`260008` 定义体检不通过、`260009` 能力不可用），detail 携带 `code/message/field/reason` |
| 七、semantica 内核集成与守卫式降级 | 内核能力调用 | `GraphBuilder` 建图、`GraphAnalyzer` 分析、exporters 导出、`LLMExtraction` 实体增强、`RelationExtractor` 关系增强、`semantica.ontology` 本体推断/校验/导出 |
| 七、semantica 内核集成与守卫式降级 | 守卫式降级 | 所有 semantica 导入均为守卫式（捕获一切 Exception）：重依赖（torch/spacy/pinecone 桩）缺失或执行失败时原样透传并标 `metadata.semantica=false`，引擎核心（持久化/查询/导出）不受影响；`GRAPH_ENGINE_SEMANTICA=0` 可整体关闭 |
| 七、semantica 内核集成与守卫式降级 | 可用性探测缓存 | 检索链、RDF 视图、LLM 模块均只真实探测一次并缓存结果（导入开销集中于重依赖加载） |
| 七、semantica 内核集成与守卫式降级 | LLM 增强 | 默认关闭：`GRAPH_ENGINE_LLM_ENHANCE` 或调用侧 `llm=true` 开启，需配 `GRAPH_ENGINE_LLM_PROVIDER`（openai/gemini/groq/anthropic/ollama/huggingface_llm）+ 可选 `LLM_MODEL`/`LLM_API_KEY`（缺省走 provider 原生环境变量）；无凭据/依赖不可用时确定降级为原候选并在响应附 `llm` meta |
| 八、本体面（O-21 ~ O-24） | 候选聚合（D6） | `POST /ontology/candidates` 从图谱记录聚合本体候选（只产候选、人工收敛，不产生定义），支持 `sources`/`maxClasses` |
| 八、本体面（O-21 ~ O-24） | 定义体检 | `POST /ontology/validate` 对定义视图做结构/悬空引用/环检查，问题按 `info/warning/error` 分级（问题码逐字对齐 `ikc_sdk.core.models.ontology`），不通过返回 `260008` |
| 八、本体面（O-21 ~ O-24） | 实例一致性体检 | `POST /ontology/validate-graph` 图谱实例对照本体（端点 / 必填 / 基数 / 数据类型），只出报告不阻断（D4/D5），支持 `maxIssues`/`includeShacl` |
| 八、本体面（O-21 ~ O-24） | 覆盖率（O-21） | `POST /ontology/coverage` 输出类型覆盖 + 违规计数 |
| 八、本体面（O-21 ~ O-24） | 导入与导出 | `POST /ontology/ingest` 导入 `owl/turtle` 定义；`POST /ontology/export` 导出 `json`（引擎本地直接回编译产物）与 `owl/turtle/shacl`（经 `semantica.ontology`，缺依赖时 `260009` 如实降级，不拦图谱主流程） |
| 八、本体面（O-21 ~ O-24） | 编译产物快照与 diff | 按图按版本存 `graph_ontology`（SQLite 表 / Neo4j `:GraphEngineGraphOntology`）：`PUT/GET /ontology/snapshots` 缓存与列举、`GET /ontology/snapshots/diff` 版本间产物 diff（D1：只缓存编译产物，定义唯一权威在 core） |
| 九、Core 数据面回写（open-ikc 接入） | 引擎→core 回写 | 构建后将已决策实体/关系经 `POST {base}/internal/graph/build` 回写 core，由 core 这一唯一写库方落地稳定 ID upsert、计数刷新、`graph_build_log`、doc 级增量废弃与审计 |
| 九、Core 数据面回写（open-ikc 接入） | 分层契约 | *抽什么*（NER/LLM 抽取、消解、证据挂接）在引擎，*怎么落地*（合并口径、计数、日志、废弃、审计）在 core，避免各引擎各写一套导致跨仓漂移 |
| 九、Core 数据面回写（open-ikc 接入） | 空载荷合法语义 | 空 `entities/relations` 是合法请求（该 doc 本次未再产出资产），core 只做 doc 级废弃；`deprecate-doc` 走此路径 |
| 九、Core 数据面回写（open-ikc 接入） | 开关与降级 | 未配置 `IKC_CORE_BASE_URL` 时整体关闭（返回 None、无副作用、响应形状不变）；回写失败**不阻断**本地构建，返回 `writeback.ok=false` 并记 warning |
| 九、Core 数据面回写（open-ikc 接入） | 内部鉴权与版本标注 | 请求头 `X-Internal-Token` 对齐 core `IKC_CORE_ADMIN_TOKEN`；回写携带 `engine`/`engineVersion`、`taskId`、`config` |
| 十、应用集成 SDK | 同步客户端 | `GraphEngineClient`：`graphs.*`（CRUD / build / merge / deprecate / stat / nodes / edges / neighbors / paths / analytics / export / sparql / search / index-status / constraints / 本体面）与 `jobs.*`（run/get/list/wait），仅依赖 `httpx` |

| 十、应用集成 SDK | 环境变量引导 | `client_from_env()` / `async_client_from_env()` 依 `GRAPH_ENGINE_BASE_URL / TOKEN / USER_ID / TENANT_ID / ROLES` 构造客户端 |

## 溯源说明

- **协议接口层**：`graph_engine/interfaces/`（http_app.py、grpc_server.py、cli.py、mcp_server.py、celery_app.py）
