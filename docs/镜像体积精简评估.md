# 镜像体积精简评估（CPU-only torch / 最小依赖集）

> 状态：评估文档 v1（2026-09-07），对应看板条目「镜像体积精简评估（CPU-only torch / 最小依赖集）」（P2，当前「未开始」）。
> 范围：分析 semantica-graph-server 单镜像（图引擎 + HAProxy 代理层同镜像）的体积构成，给出精简候选方案、收益估算与建议路径。
> 本文仅新增评估产出，**未改动** `Dockerfile` / `requirements.txt` / `pyproject.toml` 等任何构建文件，也未执行 git 提交。
> 测量边界：本环境无 Docker daemon，**未执行 `docker build` / `docker images` 量尺寸**；下文标注「实测」的均为本地 `.venv`（同源安装，2026-09-07 `du` 实测）的**解包体积**，标注「估算」的镜像尺寸区间为按构建构成拆解的推算，落地后需在有 Docker 的环境回填实测值。

**摘要**：镜像体积大的根因是 `semantica==0.6.5` 把全量 CUDA 版 `torch` 及 `nvidia-*` 运行库（本地解包约 3.9 GB+）带进了 builder→runtime 的复制产物；而引擎五面接口与 SQLite 持久化对 semantica 是守卫式可选依赖。推荐路径：**把 semantica 拆成可选 extra、默认镜像 core-only（估算 ~0.5–0.9 GB）**，语义建图部署使用配套的「CPU-only torch」semantica 变体（估算 ~1.3–2.2 GB），预期可较现状（估算 ~4.5–6.5 GB）节省 80% 以上。

## 1. 现状与体积构成分析

### 1.1 构建形态与复制策略（现状）
- 单镜像多阶段构建（见 `Dockerfile`）：`builder` 阶段 `pip install -r requirements.txt` 装齐全部依赖（含 `semantica==0.6.5`），`runtime` 阶段（`python:3.12-slim`）通过 `COPY --from=builder /usr/local /usr/local` 整体复制 site-packages 与控制台脚本，再 `apt` 安装 haproxy + gettext（envsubst）。
- 依赖层只在 `requirements.txt` 变更时失效，代码改动不重复下载大依赖——这是合理设计，但**依赖集合本身把 semantica 的整个 CUDA 依赖链固化进了镜像**，多阶段只解决了"下载/缓存"问题，没有解决"体积"问题。
- `requirements.txt` 与 `pyproject.toml [project].dependencies` 保持同步，全部为核心硬依赖，没有 extra 拆分。
- `.dockerignore` 已排除 `.venv/`、`tests/`、`data/`、`logs/`、`docker/images`（内含 97 MB 的 `open-ikc-api-1.0.0.tar`，实测）等，构建上下文本身已精简，不是体积大头。

### 1.2 体积来源拆解（为什么镜像大）
`semantica 0.6.5` 的依赖链包含 torch / transformers / spacy / opencv 等；PyPI 默认（Linux）解析出的 `torch` 为 CUDA 构建，会连带拉取一整套 `nvidia-*` 运行库 wheel。本地 `.venv` 为同源安装（`pip list` 可见 `torch 2.13.0`、`nvidia-cudnn-cu13`、`opencv-python 5.0.0.93`、`transformers 5.15.0`、`spacy 3.8.15` 等），对其 site-packages 实测如下：

| 构成 | 解包占用（实测/估算） | 说明 |
| --- | --- | --- |
| `torch`（PyPI 默认 CUDA 构建） | ~1.2 GB（实测） | `torch/lib` 含 `libtorch_cuda.so` / `libc10_cuda.so` / `libtorch_cuda_linalg.so` |
| `nvidia-*` CUDA 运行库 | ~2.7 GB（实测） | `nvidia/cu13` 1.7 GB、`cudnn` 471 MB、`nccl` 227 MB、`cusparselt` 224 MB、`nvshmem` 78 MB 等 |
| transformers / spacy / opencv-python / torchvision | ~0.3–0.4 GB（实测约 0.31 GB） | 依次约 110 MB / 119 MB / 72 MB / 数十 MB |
| `semantica` 本体 | ~17 MB（实测） | 代码 + 资源；大头在其依赖而非自身 |
| 引擎核心依赖（fastapi/uvicorn/grpcio/celery/typer/pydantic/protobuf 等） | ~0.15–0.25 GB（估算） | 均为常规 wheel，无大件 |
| `python:3.12-slim` + apt（haproxy/gettext）层 | ~0.2–0.3 GB（估算） | `--no-install-recommends` 已用，apt lists 已清理 |
| **镜像合计（docker images 显示尺寸）** | **~4.5–6.5 GB（估算）** | 本地 `.venv` 合计 7.3 GB 含开发工具链，不可直接等同镜像；仅 site-packages 大头项可比对 |

结论：**torch CUDA 构建 + nvidia 运行库约占镜像体积的 70%–80%**，是唯一值得动刀的项；其余（引擎核心依赖、HAProxy/apt 层）合计估算 <1 GB。

### 1.3 关键前提：semantica 是可选的，引擎核心不依赖它
- 守卫式导入：`graph_engine/adapters/semantica.py` 的 `semantica_available()` 对 `import semantica` 包 try/except；`build_kg` / `analyze_graph` 不可用时返回 `metadata.semantica=False` 的降级结果。`application/service.py` 的 build/analyze 同样带异常降级分支。
- 开关：`GRAPH_ENGINE_SEMANTICA` 默认 `1`，仅表示"若 semantica 可用则启用"；包缺失时无需改环境变量即自动降级（便于 core-only 镜像透明运行）。
- 引擎的稳定 ID / schema / 合并 / 证据 / 置信度 / SQLite 持久化与 HTTP / gRPC / Celery / MCP / CLI 五面接口全部在 `domain` / `application` / `persistence` / `interfaces` 内自洽实现；semantica 只增强建图合并、图分析与后续检索能力（见 `docs/解决方案.md`）。
- 现状 compose / entrypoint **未配置 GPU 直通**（无 `gpus:` / `--gpus`），即即便装了 CUDA 版 torch，容器内实际也只能 CPU 计算——CUDA wheel 在当前部署形态下属于"死重"。

## 2. 精简候选方案及利弊

### 方案 A：CPU-only torch（换 PyPI 源）
做法：semantica 依赖链安装时，把 torch 家族从 CUDA wheel 换成 CPU wheel，例如 torch 安装步骤改用 `--index-url https://download.pytorch.org/whl/cpu`（或在独立 requirements 文件中锁定 `torch==<同版本>+cpu`），使 pip 不再解析出 `nvidia-*` 运行库。需注意 pip 的 index 是文件级/命令级生效，建议**单独一条 RUN + 单独文件**安装 torch 家族，避免与 PyPI 依赖混装时又拉回 CUDA wheel。

- 优点：不动依赖结构、不动代码；功能面完全保留；镜像估算降至 ~1.2–2.0 GB（较现状省约 3–4.5 GB）。
- 代价：CPU 推理/向量算子较 CUDA 慢（本项目当前不使用向量推理路径，影响小）；需锁定与 CUDA 版同版本号的 CPU wheel 以保持行为基线。
- 风险：同版本 CPU/CUDA 在浮点累加/算子选择上存在差异，未来启用 NodeEmbedder / transformers 推理时输出向量可能与 GPU 环境不一致；需与 open-ikc 侧部署保持一致（详见 §3）。

### 方案 B：semantica/torch 拆成可选 extra，镜像默认 core-only（推荐主方案）
做法：
1. `pyproject.toml`：把 `semantica==0.6.5` 及其大依赖从 `[project].dependencies` 移入新 optional extra（如 `[project.optional-dependencies].semantica`，CPU 组合锁 CPU-only torch）。
2. `requirements.txt` 同步拆为两份：`requirements-core.txt`（fastapi/uvicorn/grpcio/celery/typer/pydantic/protobuf，默认安装）与 `requirements-semantica.txt`（semantica + CPU-only torch 组合，仅 semantica 镜像安装），维持"与 pyproject 同步"的既有约定。
3. `Dockerfile` builder 阶段默认只装 core；semantica 变体通过构建参数/独立 target（或独立 requirements 文件 COPY+RUN）追加安装，runtime 阶段结构不变。

- 优点：默认镜像从 GB 级降到 ~0.5–0.9 GB（估算，省 ~85%–90%）；构建/拉取/升级全链路变快；core-only 镜像内守卫式导入自动降级，五面接口 + SQLite 无功能损失。
- 代价：语义建图部署需显式选择 semantica 变体（tag 或构建参数），部署矩阵多一个镜像；`requirements.txt`/`pyproject.toml`/Dockerfile 需配套小改并回归。
- 与方案 A 可叠加：semantica 变体 = core + semantica + CPU-only torch，估算 ~1.3–2.2 GB。

### 方案 C：最小依赖集取舍（semantica --no-deps / 仅保留实际 import 链）
做法：对 semantica 装 `--no-deps`，只补齐其建图链路实际用到的包（如 pyoxigraph 等），验证 `semantica.kg.GraphBuilder / GraphAnalyzer` 在无 torch / transformers / spacy / opencv 时是否可 import 与建图；可用则能进一步把 semantica 变体压到 core + 数百 MB 级。
- 优点：不损失 semantica 原生建图能力的前提下追求极限体积。
- 代价：需逐一实测 semantica 0.6.5 内部对 torch 等的**真实** import 时机（文档仅能确认 `docs/解决方案.md` 记录的 pinecone/context 链路损坏、kg 链路独立，无法离线判定其延迟导入边界）；若 semantica 顶层或建图路径硬 import torch，本方案不成立。
- 结论：**收益不确定、验证成本高，不建议作为首期**；可作为方案 A/B 落地后的下一档探索。

### 方案 D：构建细节与缓存优化（低收益项）
- 多阶段保留：现状 builder/runtime 分离已合理（runtime 无编译链），semantica 拆分后**继续保持两阶段**即可；不要为了省体积把 haproxy 挪进 builder 复制——apt 层按设计只进 runtime。
- `.dockerignore`：已覆盖大头（97 MB tar 实测被排除），无需大改。
- 构建缓存：semantica 拆成独立 `requirements-semantica.txt` 后，core 层在 CPU-only 实验/多次构建间可复用（只随 core 文件失效）；如需更进一步可用 BuildKit cache mount，但按最小改动原则**不建议首期引入**。
- 微优化：清理 builder 复制的 `__pycache__`/`.dist-info` 或移除 runtime 内 pip（`docs/Docker构建进展.md` 记录保留 pip 便于排障，收益仅几十 MB）——低优先级，可最后决定。

### 候选方案汇总
| 方案 | 镜像估算 | 较现状收益（估算） | 功能面影响 |
| --- | --- | --- | --- |
| 现状（CUDA torch 全量） | ~4.5–6.5 GB | — | semantica 原生能力完整 |
| A：CPU-only torch | ~1.2–2.0 GB | 省 ~3–4.5 GB（约 65%–75%） | 无（同版本 CPU wheel） |
| B：core-only 默认 + semantica 可选 | 默认 ~0.5–0.9 GB | 省 ~85%–90% | 默认镜像无 semantica 增强，需选变体 |
| A+B：core + semantica(CPU) 变体 | ~1.3–2.2 GB | 省 ~65%–75% | 无（语义建图部署专用） |
| C：semantica --no-deps 最小集 | 待实测 | 取决于 import 边界 | 需实测确认 kg 链路可用 |

## 3. 对功能面的影响与风险

| 维度 | 现状 | A（CPU-only） | B（core-only 默认） |
| --- | --- | --- | --- |
| semantica 原生建图/合并增强 | 可用（metadata.semantica=True） | 可用，同版本 CPU wheel | 默认不可用；选 semantica 变体后可用 |
| GraphAnalyzer 分析 / export 增强 | 可用 | 可用 | 默认降级（analyze 返回 {semantica: False}） |
| HTTP/gRPC/MCP/CLI 五面 + SQLite | 不受影响 | 不受影响 | 不受影响（守卫式自动降级） |
| `GRAPH_ENGINE_SEMANTICA` 开关 | 默认 1 | 默认 1 | 保持默认 1，缺包自动降级，语义不变 |

风险与缓解：
1. **同版本 CPU/CUDA 行为差异**：`torch==2.13.0+cpu` 与 CUDA 版逻辑等价，但浮点/算子存在细微差异；当前引擎不持久化 semantica 向量、检索链路（semantica 原生 MCP/检索，P2 未开始）未启用，实际影响近零；未来启用 embedding/检索时应锁定单一部署形态，避免 CPU/GPU 双环境产出向量不可比。
2. **open-ikc 消费者期望**：open-ikc 消费的是引擎接口语义（稳定 ID/合并/证据/置信度）而非 torch；但若其部署侧依赖 semantica 建图合并的分析字段，需确认其 CPU/GPU 形态与本引擎一致（建议与 open-ikc 侧对齐为同一形态，或让默认与 open-ikc 实际使用一致后再切换默认 tag）。
3. **换源安装的污染风险**：`--index-url`/`--extra-index-url` 在同一文件混用可能把部分依赖解析回 CUDA wheel；需独立 RUN/文件 + 构建后用 `docker run ... python -c "import torch; print(torch.version.cuda)"` 断言为空。
4. **降级语义被误判**：core-only 镜像上若调用方不检查 `metadata.semantica=False`，可能误以为异常；应在镜像/部署文档明示，必要时由调用方显式探测。
5. **标签/升级断裂**：默认 tag（当前 `graph-engine:0.1.0`）含义变化，需与 `docker-compose.yml`/`scripts/build_docker.sh`（已支持 `IMAGE_TAG` 覆盖）配合，发布时用不同 tag（如 `*-core` / `*-semantica-cpu`），避免存量部署静默失去 semantica 增强。

## 4. 建议路径

### 4.1 推荐方案
**首期：B 为主 + A 配套**——镜像默认 core-only（`requirements-core.txt`，runtime 不装 semantica/torch），同时保留 `semantica-cpu` 变体（core + semantica + CPU-only torch）供需要语义建图/分析/后续检索的部署使用；不保留默认 CUDA 全量镜像（现状部署本就无 GPU 直通，CUDA wheel 无收益）。CUDA 变体仅当 open-ikc 侧确认为 GPU 部署时再按需追加，不作为默认。

### 4.2 落地步骤（实施时执行，本文未改动）
1. `pyproject.toml`：新增 `[project.optional-dependencies].semantica`，将 `semantica==0.6.5` 移出 `dependencies`（CPU 组合锁定同版本 CPU torch，具体 wheel 需在有网环境用 `pip index versions torch` / 干净 venv 实测确认）。
2. `requirements.txt` 拆 `requirements-core.txt`（默认）与 `requirements-semantica.txt`（首行/独立步骤用 `--index-url https://download.pytorch.org/whl/cpu`），保持与 pyproject 同步的既有注释约定。
3. `Dockerfile`：builder 默认 `pip install -r requirements-core.txt`；semantica 变体经构建参数（如 `--build-arg WITH_SEMANTICA=1`）或独立 requirements COPY+RUN 追加；runtime 阶段不变（仍只复制 site-packages + 控制台脚本 + apt haproxy/gettext）。
4. `docker-compose.yml`/`scripts/build_docker.sh`：用 `IMAGE_TAG` 区分 `*-core` 与 `*-semantica-cpu`，默认指向 core-only；`docs/Docker部署与HAProxy.md` 增补镜像矩阵与升级说明。
5. 回归并回填实测数据（见 §4.3），更新 `docs/Docker构建进展.md` 与 `docs/project-board.tsv`（该看板条目状态推进为「进行中/已完成」）。

### 4.3 验证清单（需在有 Docker daemon 的环境执行；本环境无法执行）

```bash
docker system df                                    # 磁盘实际占用（含压缩层）

  du -sh /usr/local/lib/python3.12/site-packages/* 2>/dev/null | sort -rh | head -15
docker inspect graph-engine:0.1.0-core --format '{{.Size}}'
```
功能回归（两枚镜像各跑一遍）：

```bash
.venv/bin/python -m pytest tests -q                 # 12 用例
# semantica 变体：构建后建图/分析应返回 metadata.semantica=True（core-only 为 False 属预期降级）
```
